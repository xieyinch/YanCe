# 言策 YanCe

> 读懂话外之意，找到更合适的回应。

**交流 QQ 群：1045175208**（使用交流、问题反馈）

> **项目来源：** 言策是对开源项目 [jev-chat/jev-chat-jarvis](https://github.com/jev-chat/jev-chat-jarvis) 的重建版本。项目在其对话辅助与 Jev 分析思路基础上重新设计和实现，并进一步加入 Android 多聊天应用适配、自定义模型供应商、本地关系记忆、安全分析、运行日志及全新界面。本仓库不是原项目的官方版本或官方续作。

言策是一款运行在 Android 手机上的**非侵入式对话副驾**。它通过系统无障碍服务读取当前屏幕上的聊天内容，先使用 Jev 判断对方的意图、需求与关系风险，再调用你自己配置的大语言模型生成候选回复，最后由 Jev 排序并显示在悬浮窗中。

言策不会替你发送消息。你可以查看、复制或把候选回复填入输入框，最终是否发送始终由你决定。

## 核心能力

- 判断对方最新消息的真实意图、潜台词和紧张程度
- 识别当前需求并给出推荐动作
- 生成稳妥、具体、简短三种不同回复
- 区分事实、推测与未知，再结合互惠、安全和边界生成建议
- 可选启用本地关系档案，让同一会话的建议保持连续
- 识别暴力、胁迫、跟踪、自伤要挟等安全风险并切换为安全建议
- 判断关系是互惠、证据不足、持续失衡还是明确拒绝
- 将冲突区分为误解、可解决问题、持续差异、核心不兼容或安全问题
- 配置 Jev 后使用 Jev 对候选回复进行二次排序
- 不配置 Jev 时自动使用已配置的大语言模型完成分析和回复生成
- 内置脱敏运行日志，方便检查接口、网络和解析错误
- 一键把选中的回复填入输入框
- 支持 Jev 官方接口和自定义大语言模型供应商
- 内置 DeepSeek 预设：选好协议就自动填地址并预置模型，只需填 API Key
- 自动拉取模型，一键添加或取消全部模型
- **每个聊天应用可单独开关**，只有打开的应用才会被读取和分析
- 通过会话白名单限制允许分析的聊天
- 悬浮窗默认只保持一个小球，有新结果才变色，不会自动弹出挡住聊天

## 快速开始

### 第一步：配置模型

打开言策设置页：

1. 可选填写 **JEV Key**。填写后启用 Jev 判断与排序；留空时由大语言模型独立完成分析。
2. 添加一个用于生成回复的大语言模型供应商。
3. 选择协议：**DeepSeek**、OpenAI 兼容、Google Gemini 或 Anthropic Claude。
   选 **DeepSeek** 会自动填好 `https://api.deepseek.com`、把供应商名设为 DeepSeek，并预置
   `deepseek-flash` 与 `deepseek-v4-pro` 两个模型，通常只需要再填一个 API Key。
4. 填写供应商 API Key 和 HTTPS 请求地址。
5. 点击“拉取供应商模型”。
6. 一键添加全部模型并选择当前模型。
7. 点击“连通测试”确认两个接口均可用。

> 自定义供应商会收到当前聊天上下文，请只使用你信任的服务。

### 第二步：补充关系背景

你可以填写“同学”“朋友”“伴侣”或“工作联系人”等关系描述，帮助模型理解背景。言策统一使用完整分析流程，不再提供会绕过安全与互惠判断的简化模式。

### 可选：启用关系记忆

在设置页开启“本地关系档案”后，言策会按会话保存少量事件摘要，并在下一次分析同一会话时作为背景。此功能默认关闭，不保存完整聊天原文；可以暂停记录、删除单个联系人或一键清空全部档案。

### 第三步：开启权限

- **无障碍服务**：读取当前聊天窗口并填入回复
- **悬浮窗权限**：在聊天应用上方显示结果
- **自启动与省电无限制**：减少国产 Android 系统冻结后台服务
- **选择要识别的应用**：设置页「识别的聊天应用」里打开你要用的那几个，其余不会被读取

进入打开的聊天窗口后，对方发送新消息时，言策会自动分析；悬浮窗默认只把小球的颜色变一下，
点它才展开看结果。关闭自动分析后，也可以点击悬浮按钮手动分析。

## 工作流程

~~~text
当前聊天窗口
      ↓
无障碍服务提取最近消息
      ↓
Jev 判断意图、风险、需求和建议动作
（未配置 Jev 时由大语言模型完成）
      ↓
自定义大模型生成 3 条候选回复
      ↓
Jev 对候选回复排序
（未配置 Jev 时保留大语言模型顺序）
      ↓
悬浮窗展示 → 复制或填入输入框
      ↓
用户自行确认并发送
~~~

如果生成期间聊天内容发生变化或用户切换会话，旧回复会被丢弃，避免结果串到其他聊天中。

## 平台支持

| 平台 | 状态 | 采集方式 |
| --- | --- | --- |
| 微信 Android | 已接入 | 无障碍节点；部分版本需要兼容处理 |
| 手机 QQ | 已接入 | 无障碍文本节点 |
| X / Twitter 私信 | 已接入 | 解析无障碍描述 |
| 飞书 Android | 基础接入 | 标题和输入框可用，普通消息正文仍需 OCR |
| 小红书私信 | 已接入 | 无障碍节点；结构按真机节点树校准 |

聊天应用更新可能改变界面结构，因此适配状态也可能随版本变化。

### 只识别你打开的应用

设置页「识别的聊天应用」里每个应用都有独立开关，**只有打开的才会被读取**。关掉的应用在采集层
就被拒绝（拿到前台包名先查开关，不通过就直接返回），不读节点、不分析、不外发任何内容。
首次使用（设置没保存过）时全部视为打开，所以升级不会偷偷改变行为。

### 悬浮窗为什么不自动弹出

默认**不自动展开**：出现新结果时悬浮窗只把小球变成薄荷绿，点一下才展开面板，这样不会挡住正在看的聊天。
如果更希望结果直接弹出来看，在「外观」里打开「结果就绪时自动展开面板」。

### 小红书私信是怎么适配的

拆包确认它把资源名全混淆了 —— 25,473 个 `id` 只有 49 个不同名字，其中 25,425 个都叫
`0_resource_name_obfuscated`，7,681 个 layout 同样如此。运行时每个视图的 `viewIdResourceName`
**完全相同**，所以靠 resource-id 区分控件这条路从根上不通，适配器完全不读 id。

它改成按真机实测的节点结构判断（结构来自本机抓取的节点树，不是猜的）：
**消息列表**取"面积最大的竖向可滚动容器"，**只收集该容器子树内的文本** ——
这一点很关键，因为顶部「加个关注」推广条虽然盖在列表上、坐标落在列表矩形里，但它是列表的**兄弟节点**，
按坐标过滤会把「关注」当成一条消息；快捷短语行则是列表下方的**第二个** RecyclerView。
**谁发的**看头像：小红书把头像贴在自己那一侧的外缘（对方 x≈48，我 x≈1032），
而长气泡在两侧会占同样的横向范围（实测两条都是 `[180..900]`），只看气泡位置分不出来。

要适配新的聊天应用，用设置页「诊断悬浮球」：停在目标应用的聊天界面点那个红色「诊」球，
它会把该界面的节点树复制到剪贴板（只在本机，不上传），照着补一个适配器即可。

## Jev 与大模型如何配合

言策把判断和表达拆开：

1. **Jev 先判断（可选）**
   识别真实意图、关系风险、当前需求、最佳动作，以及是否需要给出实质回复。

2. **大模型再表达**
   大模型收到聊天原文和 Jev 判断后，生成三条不同策略的回复。聊天原文始终是事实边界；如果 Jev 结论与原文明显冲突，应以原文为准。

3. **Jev 最后排序**
   Jev 根据当前需求和建议动作，对三条候选重新排序。

这种流程比直接让大模型猜测“该怎么回”更稳定，也更容易控制行为边界。

没有 Jev Key 时，言策会通过一次结构化大语言模型请求同时获得意图、风险、需求、推荐动作和三条候选回复，不会阻止正常使用。

## 运行日志

设置页底部提供“查看运行日志”入口，可查看无障碍服务连接、分析阶段、接口失败、网络超时和 JSON 解析错误。日志保存在应用私有目录，最大约 128 KB，超出后自动截断；不会主动记录聊天原文或 API Key，并支持随时清空。

## 隐私与安全边界

- 不 Hook、不使用 Xposed、不修改聊天应用
- 不读取聊天软件数据库
- 不登录或接管聊天账号
- 不点击发送按钮
- 不处理转账、红包和收款操作
- 检测到明确危险信号时，不生成推进、挽回或单独摊牌建议
- 不在日志中输出聊天原文或 API Key
- 关系记忆默认关闭，只在本机保存有数量和长度限制的事件摘要
- 仅处理用户自己设备上有权查看的内容
- 密钥保存在应用私有存储中

当前应用私有存储尚未升级为 Android Keystore 加密，这是后续需要完善的安全项。

## 技术架构

- Kotlin + 传统 View/XML
- Android 11 及以上（minSdk 30）
- Android AccessibilityService
- Jev / TypeSafe System One
- DeepSeek、OpenAI 兼容、Gemini 和 Claude 自定义接口

## 已知限制

- 不同 Android 系统对后台服务的限制不同，可能需要允许自启动和后台运行。
- 微信等应用更新后可能改变无障碍节点，导致采集暂时失效。
- 微信自己的官方提示（如「对方账号安全性未知…」）目前是**按措辞**排除的，词表不可能穷尽；
  彻底的做法是按结构识别（这类提示没有头像、水平居中），需要一份显示该提示时的节点树。
- 飞书普通消息正文由自绘控件渲染，当前尚未完成截图 OCR。
- X / Twitter 解析主要按照已测试的中文界面实现。
- 当前主要面向一对一聊天，群聊中的人物归属和关系判断可能不准确。
- 生成质量取决于模型、供应商稳定性和聊天上下文完整程度。
- 当前不会长期保存完整聊天记录，也没有跨会话自动关系记忆。

## 项目原则

1. **只辅助，不代替用户决定。**
2. **只填入，不自动发送。**
3. **事实优先，不把推测包装成结论。**
4. **尊重拒绝、边界和双方选择。**
5. **不通过操控、施压或虚构承诺换取短期效果。**
6. **采集层可以扩展，判断与生成内核保持通用。**
